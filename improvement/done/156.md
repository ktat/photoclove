# src-tauri/src コードレビュー

## 概要

PhotoCloveのバックエンドは**約16,500行**、**88ファイル**で構成される、**DDD (Domain-Driven Design)** アーキテクチャに基づいたよく構造化されたコードベースです。全体的にClean Architectureの原則に従っていますが、いくつかの改善点があります。

---

## 良い点

### 1. アーキテクチャ設計
- **レイヤー分離が明確**: Commands → Domain Services → Entities → Repositories の階層が明確
- **Repository パターン**: `MetaInfoDB`, `RepositoryDB` トレイトによる抽象化
- **SQLiteモジュールの分割**: `search.rs`, `photo_crud.rs`, `collections.rs` 等に分割され可読性が高い
- **マイグレーションシステム**: バージョン管理されたSQL移行が適切に実装

### 2. エラーハンドリング設計
- `error.rs` の `PhotoCloveError` は包括的で、severity/category/suggestion を持つ優れた設計
- ユーザーフレンドリーなエラーメッセージとリカバリーヒント

### 3. ログ設計
- 構造化ログ (`key=value` 形式) を一貫して使用
- `target` による分類 (`job_queue`, `database`, `trash` 等)

## 重大な問題

### 1. panic! の使用 (複数箇所)
**ファイル**: `entity/photo.rs:153`, `entity/photo.rs:179`, `entity/photo.rs:252`, `value/date.rs:238`

```rust
// photo.rs:153, 179, 252
panic!("Import path is not set in Photo entity");
panic!("Invalid date string extracted from path: empty date_only");
panic!("Invalid time format for date parsing: {}", self.time);

// date.rs:238
panic!("Date parsing failed: {}, delimiter: {}, error: {}", ...);
```

**問題**: プロダクションコードで `panic!` を使用すると、アプリケーションがクラッシュする可能性があります。

**推奨**: `Result<T, E>` を返すか、`Option<T>` を使用してエラーを伝播させる。

### 2. unwrap() の危険な使用
**ファイル**: 複数箇所

```rust
// lib.rs:163
let job_queue_manager = state.job_queue_manager.lock().unwrap();

// executor.rs:224
let job_id = job.id.unwrap();

// executor.rs:272
tokio::runtime::Runtime::new().unwrap().block_on(...)

// repository.rs:47
serde_json::to_string(&self.data).unwrap()
```

**推奨**: `expect()` でコンテキストを追加するか、`?` でエラーを伝播させる。

### 3. SQL インジェクションのリスク
**ファイル**: `repository/meta_db/sqlite/search.rs:130-133`

```rust
if !extension.is_empty() && extension != "all" {
    sql_query.push_str(" AND path LIKE ?");
    params.push(Box::new(format!("%.{}", extension)));
}
```

パラメータ化されていますが、`format!("%.{}", extension)` でワイルドカードを直接結合しています。悪意のある入力（`%` や `_`）がパターンを壊す可能性があります。

**推奨**: 入力をサニタイズするか、エスケープ処理を追加。

## 中程度の問題

### 4. スレッド間のMutexロック
**ファイル**: `lib.rs:163`

```rust
let job_queue_manager = state.job_queue_manager.lock().unwrap();
job_queue_manager.start_background_processing(app_handle);
```

`setup` ブロック内で `unwrap()` を使用しており、デッドロックや panic の可能性。

### 5. 接続プーリングの欠如
**ファイル**: `repository/meta_db/sqlite/mod.rs:89-102`

```rust
pub fn get_connection(&self) -> Result<Connection> {
    // ...
    Connection::open(&self.db_path)
}
```

毎回新しいコネクションを作成しています。

**推奨**: `r2d2` や `rusqlite::ConnectionManager` を使用した接続プーリング。

### 6. 正規表現の毎回コンパイル
**ファイル**: `entity/photo.rs:101`, `117`, `156`, `239`, `246`

```rust
let ext_regex = regex::Regex::new(r"\.(?i)jpe?g$").unwrap();
```

**推奨**: `lazy_static!` または `once_cell::Lazy` で正規表現をキャッシュ。

```rust
static JPEG_REGEX: Lazy<Regex> = Lazy::new(|| Regex::new(r"\.(?i)jpe?g$").unwrap());
```

### 7. 変数名の typo
**ファイル**: `repository.rs:85`, `93`, `106`

```rust
conifg: Option<config::Config>  // "config" のタイプミス
```

### 8. Date::from_string がpanicする設計
**ファイル**: `value/date.rs:235-245`

`from_string` はエラー時にpanicしますが、`try_from_string` が存在します。

**推奨**: `from_string` を非推奨にするか、内部で `try_from_string` + `expect` を使用。

### 9. Clone の手動実装
**ファイル**: `value/date.rs:22-33`, `138-143`

`DateTime` と `Date` に手動で `Clone` を実装していますが、`#[derive(Clone)]` で十分です。

```rust
impl Clone for DateTime {
    fn clone(&self) -> DateTime { ... }
}
```

**推奨**: `#[derive(Clone)]` を使用。

## 推奨アクション（優先度順）

1. **[Critical]** `panic!` を `Result` に置き換える
2. **[Critical]** `.unwrap()` に `.expect("context")` またはエラーハンドリングを追加
3. **[High]** 正規表現のキャッシュ (`lazy_static!` / `once_cell`)
4. **[High]** SQLite接続プーリングの検討
5. **[Medium]** 変数名 `conifg` → `config` の修正
6. **[Medium]** `hasComment` → `has_comment` の修正
7. **[Low]** 大きなファイルの分割
8. **[Low]** 手動 `Clone` 実装を `#[derive(Clone)]` に置換

---

## まとめ

全体的に**良質なアーキテクチャ**と**一貫したコーディングスタイル**を持つコードベースです。DDDパターンの適用、構造化ログ、包括的なエラー型設計は優れています。

主な改善点は、**panic!/unwrap()の排除**と**パフォーマンス最適化**（正規表現キャッシュ、接続プーリング）です。これらを解決すれば、より堅牢なプロダクションコードになります。
