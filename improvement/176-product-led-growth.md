# Product-Led Growth (PLG) 要素の導入

## Overview
PhotoCloveにProduct-Led Growth (PLG) 戦略の要素を導入し、製品自体がユーザー獲得・活性化・維持の主要なドライバーとなる仕組みを構築する。

## PLG とは

Product-Led Growthは、製品自体がマーケティング・セールス・カスタマーサクセスの役割を担う成長戦略:

- **製品主導**: 営業やマーケティングではなく、製品体験がユーザー獲得を促進
- **フリーミアム/フリートライアル**: 無料で価値を体験できる
- **バイラル性**: ユーザーが自然と他のユーザーを呼び込む仕組み
- **セルフサービス**: ユーザーが自分で価値を発見・実現できる

## Discussion Points

### 1. PhotoCloveの現状とPLGの適合性

**PhotoCloveの特性**:
- ローカルファースト（デスクトップアプリ）
- プライバシー重視（写真はローカル保存）
- オープンソース（無料提供）

**検討ポイント**:
- PLGは通常SaaS向けの戦略だが、デスクトップアプリにどう適用するか？
- オープンソースプロジェクトにおけるPLGの意味とは？
- 収益化を目指すのか、ユーザーベース拡大を目指すのか？

### 2. 考えられるPLG要素

#### A. ユーザー獲得（Acquisition）

##### A-1. 共有機能（Share）
- **案1**: 写真をウェブリンクで共有（一時的な公開URL生成）
- **案2**: アルバムの共有リンク生成
- **案3**: SNS共有ボタン（Twitter/Instagram等）
- **影響**: サーバーインフラが必要になる可能性

##### A-2. エクスポート時のブランディング
- **案1**: エクスポート写真にオプションでウォーターマーク
- **案2**: 共有時に「PhotoCloveで整理」のクレジット
- **影響**: ユーザー体験を損なう可能性

##### A-3. 招待プログラム
- **案1**: 友達紹介で特典（プレミアム機能解放など）
- **影響**: 紹介追跡システムが必要

#### B. ユーザー活性化（Activation）

##### B-1. オンボーディング改善
- **案1**: インタラクティブなチュートリアル
- **案2**: 「最初の10枚をインポート」などの段階的ガイド
- **案3**: 機能発見のヒント表示
- **影響**: Welcome.jsx, 新規コンポーネント追加

##### B-2. Time-to-Value短縮
- **案1**: サンプル写真付きデモモード
- **案2**: ドラッグ&ドロップでインポート開始
- **案3**: 写真フォルダの自動検出と提案
- **影響**: Importer.jsx, Config

##### B-3. Aha!モーメントの設計
- **案1**: 最初の検索成功時の祝福メッセージ
- **案2**: 整理前後のビジュアル比較
- **案3**: 「〇〇枚の写真を整理しました」の達成感表示
- **影響**: UIContext, 新規コンポーネント

#### C. ユーザー維持（Retention）

##### C-1. 使用状況ダッシュボード
- **案1**: 「今月インポートした写真数」
- **案2**: 「ストレージ節約量」の表示
- **案3**: 写真整理の履歴・統計
- **影響**: 新規ダッシュボードコンポーネント、統計データ収集

##### C-2. 定期的なリマインド
- **案1**: 「最近インポートしていません」通知
- **案2**: 週次/月次のサマリーレポート
- **案3**: 「この日の思い出」機能
- **影響**: 通知システム、バックグラウンドサービス

##### C-3. 習慣化機能
- **案1**: 連続使用日数（ストリーク）
- **案2**: 整理チャレンジ/目標設定
- **影響**: 新規機能、データベース拡張

#### D. 収益化（Revenue）- Optional

##### D-1. フリーミアムモデル
- **案1**: 基本機能は無料、高度な編集機能は有料
- **案2**: Google Photos連携は有料
- **案3**: AIタグ付け機能は有料
- **影響**: ライセンス管理、支払いシステム

##### D-2. クラウドオプション
- **案1**: クラウドバックアップ（有料）
- **案2**: 複数デバイス同期（有料）
- **影響**: バックエンドインフラ

### 4. PhotoClove固有の制約

**考慮すべき点**:

1. **プライバシー重視**
   - ユーザーデータの外部送信は最小限に
   - オプトイン方式
   - ローカルファーストの原則維持

2. **オフライン動作**
   - ネットワーク依存機能は制限
   - ローカルで完結する機能を優先

3. **オープンソースの精神**
   - コミュニティ貢献を促進
   - 過度な商業化は避ける

## 方針決定

### 目標
- **主目標**: ユーザー数増加
- **副目標**: ちょっとした収益化

### 制約
- **サーバーインフラ**: 可能だが消極的（コスト・運用負担を最小化したい）
- **優先**: ローカルで完結する機能、または最小限のサーバー依存

|---------------|------|-----------------|
| Week Complete | 7日連続で写真がある | 📆 |
| 100 Dates | 100個のユニークな日付（年を含む） | 💯 |
| 365 Dates | 365個のユニークな日付（年を含む） | 🎊 |
| Leap Year | うるう年2/29の写真がある | 🦘 |
| **Calendar Complete** | 全366日のカレンダー日（1/1-12/31 + 2/29、年は問わない） | 🗓️🏆 |

**日付アチーブメントの違い**:
- `100 Dates` / `365 Dates`: 年を含むユニークな日付（2024-01-01 と 2023-01-01 は別々にカウント）
- `Calendar Complete`: 月-日の組み合わせ（年は無視、01-01 は1つとしてカウント）

#### G. 実装メモ

**データベース**
```sql
CREATE TABLE achievements (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    description TEXT,
    category TEXT,  -- 'first', 'monthly', 'count', 'date', 'special'
    icon TEXT,
    achieved_at DATETIME,
    shared_at DATETIME  -- SNSシェア済み日時
);
```

**チェックタイミング**
| トリガー | チェック対象 | 実装状況 |
|----------|-------------|----------|
| インポート完了時 | First Import, 月別, 累計枚数, 日付系 | ✅ |
| 編集保存時 | First Edit | ✅ |
| タグ追加時 | First Tag, Tag Master | ✅ |
| スター変更時 | First Star | ✅ |
| アルバム作成時 | First Album, Album Curator | ✅ |
| 検索実行時 | First Search | ✅ |
| エクスポート時 | First Export | - |
| Google Upload時 | First Google Upload | ✅ |
| 削除時 | First Delete | ✅ |

**バックエンド統合（実装済み）**
- バックエンド（Rust）でアクション実行時にアチーブメントをチェック
- `app_handle.emit("achievement_unlocked", achievement)` でフロントエンドにイベント送信
- フロントエンド（React）で `listen("achievement_unlocked")` でイベント受信
- 達成時にポップアップ表示

**パフォーマンス考慮**
- 達成済みアチーブメントはスキップ
- 累計系は定期的にバックグラウンドでチェック
- 達成時のみポップアップ表示
