  extract EXIF thumbnail

  4. If resize fails: Show error image (/img_error.png)
  5. Retry prevention: dataset.triedResized flag prevents infinite loops

  convertThumbnailDataSrc 実装まとめ

  新しいアーキテクチャ

  1. convertThumbnailDataSrc(photoPath) 関数
    - モジュールレベルの thumbnailCache オブジェクトでキャッシュ管理
    - 初回アクセス時のみ get_resized_image を呼び出し
    - 成功: data URLをキャッシュして返す
    - 失敗: convertFileSrc(photoPath) をフォールバックとしてキャッシュ
  2. useEffect での事前読み込み
    - import photosを検出
    - 各写真に対して convertThumbnailDataSrc を呼び出し
    - 結果を photosListImgSrc stateに保存
  3. レンダリング時のフォールバック
    - stateに値があれば使用
    - なければ "Loading..." プレースホルダー（半透明）を表示

  メリット

  ✅ キャッシュ効率: 同じ写真は一度だけ抽出
  ✅ 自動フォールバック: EXIF抽出失敗時は自動的にオリジナル画像
  ✅ 詳細なログ: 各ステップで状況を追跡可能
  ✅ パフォーマンス: data URLなら高速、失敗しても表示される

  これでテストしてみてください。ログで以下を確認できます：
  - thumbnail_extract_start: 抽出開始
  - thumbnail_extract_success: 成功（data URL取得）
  - thumbnail_extract_invalid: data URLが無効
  - thumbnail_extract_error: エラー発生
  - thumbnail_cache_hit: キャッシュヒット

  画像が表示されるはずです！

● はい、その通りです！

  現在の実装では、**キャッシュは完全にJavaScript側（フロントエンド）**で行っ

  // モジュールレベルのキャッシュ（PhotoGrid.jsxのトップレベル）
  const thumbnailCache = {};

  これは：
  - ✅ アプリ起動中は永続的（ページをリロードしない限り保持される）
  - ❌ アプリを再起動すると消える
  - ❌ メモリに保存されるため、大量の写真だとメモリを消費する

  より良いアプローチの提案

  もしキャッシュをRust側で行いたい場合：

  1. Rust側でメモリキャッシュ - lazy_static や once_cell
  を使ってHashMapでキャッシュ
  2. ディスクキャッシュ - 抽出したEXIFサムネイルをファイルシステムに保存（~/
  .local/share/photoclove/thumbnails/ など）

  どちらが良いと思いますか？

  - JavaScript側のメモリキャッシュ（現状）:
  シンプル、高速、ただしアプリ再起動で消える
  - Rust側のメモリキャッシュ:
  アプリ起動中は永続的、JavaScriptから何度呼んでも高速
  - Rust側のディスクキャッシュ:
  アプリ再起動後も永続的、最も高速、ただし実装が複雑

  どのアプローチが良いですか？

> data-url は一度は表示されていますので、特に問題ないと思います。
JavaScript側でcacheを持つ場合、表示の整合性とメモリの枯渇の両方を同時に成立
できない可能性があります。
ですので、Rust側で 
DataURLを取得する関数がJavaScriptから呼ばれたタイミングでキャッシュ(テンポラ
リファイルとして、キャッシュする。すでに存在すればそれを使う)
キャッシュのファイル数が多くなっているようだったら古いものから削除する(200く
らいあれば十分だと思う)
